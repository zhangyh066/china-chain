# 链谱 ChainAtlas

大多数人看公司，是横着看的：一排代码、一列涨跌幅、一堆指标，彼此孤立。

链谱尝试**竖着看公司**：把企业放回产业链，看它站在哪个环节、与谁存在已披露的供需关系，以及公司、行业和环节最近正在怎样变化。

它不是另一个万得或企查查。核心资产不是更多公司字段，而是三张叠在一起的图：**产业结构图、披露关系图、趋势对照图**。

**在线体验**：[打开链谱](https://zhangyh066.github.io/china-chain/) · [数据健康度](https://zhangyh066.github.io/china-chain/#/health) · [产品观点](https://zhangyh066.github.io/china-chain/#/vision) · [数据纠错](https://github.com/zhangyh066/china-chain/issues/new/choose)

## 项目背景

公司档案、工商信息和财务终端已经很成熟，再做一个“字段更多的公司列表”没有明显价值。这个项目想验证一个更窄的问题：

> **把公司放回它所在的产业链，能否比孤立的公司指标更容易看清结构、相对强弱和变化来源？**

因此，页面围绕三个问题组织，而不是围绕数据表组织：

- **位置**：这家公司在链条的哪一层，和同环节公司相比有何不同？
- **关系**：哪些上下游关系有上市公司披露支撑，哪些只是行业结构推断？
- **变化**：公司是在跑赢自己的行业与环节，还是仅仅被市场整体带着走？

目标用户是需要快速理解产业结构、但没有专业终端或完整研究团队的投资者、学生与行业研究者。它更适合做**研究入口和结构底图**，不试图替代专业数据库。

## 核心功能

### 1. 从市场到环节：看趋势，不只看快照

- 首页提供全市场近一年等权指数、行业一年涨跌榜、环节近一周/近一月温度榜。
- 行业页将行业指数与主要环节指数画在同一张图上，图例可联动筛选公司。
- 公司页把个股、所属行业、所属环节归一到同一基期，直接观察相对强弱。
- 自选股抽屉新增“环节透视”：看自己关注的公司集中暴露在哪些环节，而不只是一串股票代码。

### 2. 27 条产业链看板：先分层，再看公司与温度

覆盖锂电、光伏、半导体、机器人、AI 算力、储能、医药、汽车、军工、食品饮料、家电、化工、有色、电网、消费电子、农业养殖、建筑建材、钢铁、煤炭、风电、纺织、工程机械、医疗器械、通信设备、家居、造纸、化妆品医美。

- **流向链**：上游 → 中游 → 下游 → 配套，带间箭头表示产业流向。
- **品类链**：食品饮料、有色、建筑建材、家居、医疗器械按并列品类呈现；没有可靠方向时不硬画上下游。
- 每个阶段保留核心公司、概念纯度、阶段趋势与温度。
- 锂电、光伏额外接入期货价格与沿链传导视图。
- 链内披露连线单独展示；链评卡将自动数据事实与人工判断分槽维护，避免把规则输出伪装成研究观点。

### 3. 公司页：把披露关系叠回价值地图

- 行情、财务、主营业务、主营构成、所属环节与同环节公司集中呈现。
- 展示前五大客户/供应商集中度、近四年序列和最新实名明细。
- “据对方披露”补齐反向关系：即使本公司没有实名披露，也可能从对手方年报中恢复一条边。
- 价值链地图中，**实线表示披露关系，虚线表示结构推断**，导出 PNG 时保持同样语义。
- 支持 2–4 家公司对比、加入自选、价值链地图导出和行业公司列表 CSV 导出。

### 4. 把数据可信度做成页面，而不是藏在脚注里

[数据健康度页](https://zhangyh066.github.io/china-chain/#/health)逐项列出行情、历史、公司档案、趋势、链条、披露和纯度等数据源的最后日期、覆盖数量与更新预期。数据过期会明确显示，不用一次成功抓取冒充持续更新。

### 5. 分享当前视图，带着上下文纠错

- 页脚“复制本页链接”复制当前公司、行业、链条或对比视图地址，剪贴板不可用时提供降级方案。
- “数据纠错”会随路由更新，主动打开 GitHub Issue 时自动携带当前链接、路由、数据快照和界面语言，减少“哪一页、哪版数据”的往返确认。
- 不在后台收集或上传反馈；只有用户主动打开并提交 Issue 后，页面上下文才会发送到 GitHub。

## 产品与技术选型

| 环节 | 选择 | 不选什么 | 原因 |
|---|---|---|---|
| 产品本体 | 环节与关系，而非公司字段大全 | 复制万得/企查查 | 差异化来自观察结构，而不是比拼数据库规模 |
| 前端 | 原生 ES Module + Canvas/SVG | React/Vue + 大型图表框架 | 页面以只读可视化为主，零运行时依赖足够，部署与维护更简单 |
| 数据服务 | 构建期生成静态 JSON | 在线数据库与 API 服务 | 4,071 家公司可按文件拆分，GitHub Pages 即可托管，无服务器成本 |
| 首屏加载 | 轻量索引 + 公司文件按需加载 | 首屏下载全量财务 | 避免为了首页卡片下载 1.6MB 全市场明细 |
| 趋势指标 | 等权指数，基期 100 | 市值加权 | 观察“典型公司与环节温度”，避免少数巨头代表整个行业；不用于复制市场指数 |
| 关系表达 | 披露、推断、手工三层分开 | 所有连线混成一张“知识图谱” | 同链不等于供货，真实性边界必须能直接被用户看见 |
| 用户状态 | `localStorage` 保存自选、对比和设置 | 注册、登录、云同步 | 当前无需账号；自选股留在本机，也不要求后端 |
| 部署 | GitHub Actions + GitHub Pages | 自建应用服务器 | 静态站足够承载功能，验证通过才发布 |

## 实现思路

数据与页面分五层，每层可以单独重建或替换：

```text
公开行情 / 行业分类 / 公司档案 / 供应披露原始表
                    ↓
        抓取、筛选、清洗、名称与代码匹配
                    ↓
  公司索引 · 环节归属 · 披露边 · 日线 · 链条配置
                    ↓
 趋势指数 · 概念纯度 · 传导统计 · 链内披露 · 健康度
                    ↓
 静态 JSON + 预渲染 HTML → 原生 JS 页面 → GitHub Pages
```

几个关键约束：

1. **构建期做重活，运行期只读 JSON**：前端不负责全市场聚合，打开页面不需要数据库。
2. **按变化节奏拆数据**：公司身份、行情、历史、档案、披露和链条分别更新，改一处不必重爬全站。
3. **缓存优先，离线可重建**：已有行情、行业、概念和日线缓存会复用；大多数派生产物可完全离线生成。
4. **失败不发布脏数据**：管线原子落盘，空结果不覆盖缓存；更新失败时保留上一版，并继续展示真实截至日期。
5. **降级不白屏**：公司历史、财务或披露缺失时只收起对应模块，其余页面继续可用。

## 数据口径：真实、披露与推断分开

| 数据层 | 内容 | 性质与边界 | 来源 |
|---|---|---|---|
| 行情与财务 | 价格、涨跌幅、市值、PE、利润率、营收增速、EPS 等 | 真实公开数据；各公司带截至日期 | 东方财富、akshare |
| 公司档案 | 主营业务、产品、经营范围、主营构成、工商与上市信息 | 真实公开信息；披露粒度因公司而异 | 同花顺、巨潮资讯、东方财富 |
| 行业与环节 | 24 个行业、199 个环节及公司归属 | 公开分类与概念板块基础上人工整理；归属不代表交易关系 | 申万行业分类、公开概念板块 |
| 客户与供应商 | 前五大集中度、实名明细、金额、占比、披露年份 | 年报披露口径；匿名、未披露和未进入前五均不代表没有业务 | CNRDS 学术数据集整理 |
| 披露关系边 | 库内公司之间的正向与反向披露索引 | 有披露支撑，但只是公开披露关系的子集，不是完整供应网络 | 同上 |
| 推断上下游 | 行业步进表推导的公司间连线 | **结构示意，未经逐家核实**；页面以虚线区分 | 行业结构与环节归属 |
| 手工价值链 | 151 家公司的五列价值地图 | 人工梳理，可与披露边叠层查看 | 人工整理 |
| 期货价格 | 碳酸锂、工业硅主力合约 | 期货主力，不是现货价格 | 广期所公开行情 |

两条最重要的语义边界：

- **同属一个环节，不等于存在供货关系。**只有进入披露清单的边才能称为“披露关系”。
- **未见披露，不等于没有参与。**可能来自匿名披露、未进入前五、业务未单列或数据尚未覆盖。

## 趋势指数与概念纯度怎么算

### 趋势指数

全市场、行业和环节指数使用同一套口径：

- 以窗口起点为 **100**，对成分公司的日收益做等权平均。
- 停牌期间以前值填充，新股从进入样本后开始计入。
- 单日绝对收益超过 30% 的异常点不进入聚合。
- 行业与环节图用于比较方向和相对强弱，不是可投资指数，也不与上证指数等市值加权口径混用。

选择等权不是“不知道可以加权”，而是产品问题不同：市值加权适合描述投资组合，等权更适合回答“这个环节里的典型公司是否普遍在动”。环节温度榜还同时显示样本数，避免把少数公司的波动误读成整个产业。

### 概念纯度

纯度从公司主营构成与业务文本中提取，分三档展示：

| 档位 | 含义 |
|---|---|
| 披露占比 | 主营构成中能识别该业务，并给出对应占比 |
| 布局·未单列 | 业务文本能确认有所涉及，但没有单独披露收入或业务占比 |
| 未见披露 | 当前材料中未找到足够证据；**不推断为没有该业务** |

它是披露粒度的结构化摘要，不是技术实力、收入质量或投资评分。关键词与规则保存在 `pipeline/build_purity.py`，可离线重建。

## 供应关系数据处理

供应披露来自 CNRDS 前五大客户/供应商表，原始数据约 34 万行，披露年份横跨 2003–2025。处理重点不是“把 Excel 转 JSON”，而是避免把报表口径误当成真实产业关系：

1. **只保留合并报表**，剔除母公司报表，减少自家子公司被误认为外部客户的情况。
2. **过滤自环与明显的自家子公司**，名称匹配采取保守策略，宁可漏剔也不错杀。
3. **识别匿名占位名称**：“客户一”“供应商 A”“合计”等仍可进入集中度，但不进入实名关系边。
4. **匹配上市公司代码**：优先使用披露中的上市代码，再使用关联上市代码，最后才做规范化名称匹配。
5. **建立反向披露索引**：A 把 B 列为客户，对 B 而言就恢复了一条“供应商 A”的证据。
6. **统一单位**：金额换算为万元，占比统一为 0–1；正向与反向关系统一方向语义。

最终形成 1,917 条库内正向披露边与 1,857 条反向索引，并将双方都在同一链条名单中的关系聚合到产业链看板。它们依然只是公开披露的子集，不代表完整供应链。

**许可边界**：CNRDS 原始表仅在本机处理，目录已加入 `.gitignore`，不提交原始文件。仓库保留的是处理后的聚合与匹配结果；使用和再分发仍应遵守原数据提供方许可。

## 实证检验：一条被数据否掉的方向

项目曾尝试把 Cohen & Frazzini（2008）的“客户动量领先供应商收益”迁移到 A 股，并据此做预测。最终没有把这个方向包装成产品亮点，因为数据没有支持它。

| 检验 | 样本与口径 | 结果 |
|---|---|---|
| 周度池化交叉相关 | 约 43.8 万边—周观测 | 同周相关 `r=0.2691`，客户领先一周 `r=0.0009` |
| 最优领先期分布 | 1,842 条真实披露关系、近一年日线 | 67.75% 的边最佳 lag 为同周 |
| 月度复刻 | 403 家供应商、约 2.55 万边—月，2010 年起后复权收益 | 滞后一月 `r=-0.0015`，`t=-0.24` |
| 五档多空组合 | 按客户历史收益分组 | 多空约 `-0.19%/月`，`t=-0.63`，未显示稳定收益 |

结论不是“供应链信息永远无效”，而是：**这批 A 股样本没有复现可交易的跨周/跨月领先效应。**因此项目停止了收益预测方向，把披露数据用于结构验证、关系归因和变化观察。阴性结果保留在首页研究卡中，避免只展示支持初始想法的证据。

## 踩坑与优化

| 现象 | 根因 | 处理 |
|---|---|---|
| 首页下载大量用不到的财务字段 | 全市场财务文件首屏整包加载 | 轻量字段并入 `index.json`，完整财务拆为 `data/f/{代码}.json` 按需读取 |
| 刷新后仍看到旧页面且没有报错 | 浏览器启发式缓存 | 开发服务器统一 `no-store`，CI 直接验证构建后的 `dist/` |
| 概念纯度为 0 被理解成“没有业务” | 把披露缺失误写成事实缺失 | 改为“披露占比 / 布局·未单列 / 未见披露”三档 |
| 供应明细被 openpyxl 读丢列 | 原始 XLSX 的 dimension 元数据损坏 | 使用 XML `iterparse` 按单元格坐标解析，不依赖损坏的工作表范围 |
| 母公司客户看似很多，实际混有内部关系 | 报表口径未过滤 | 只保留合并报表，并过滤自环与明显子公司 |
| 零实名披露公司完全没有关系 | 只从本公司视角看数据 | 建立“据对方披露”反向索引 |
| 长期收益序列出现不合理负价格 | 前复权在长期、大涨幅样本上可能产生负价 | 公司页短期展示仍用前复权；长期收益检验改用后复权 |
| 行业环节看似上下游，实际只是并列品类 | 为了图形统一强行加方向 | 27 条链拆成流向链与品类链，后者不画供需箭头 |
| 切换路由后旧请求覆盖新页面 | 异步返回时未核对当前路由参数 | 路由守卫同时校验路由与参数，并补齐加载状态清理 |
| 抓取中断留下半份 JSON | 直接覆盖目标文件 | 原子落盘；空结果不写缓存，失败保留旧版 |
| 北交所行情代码偶发错标市场 | 多处脚本各自维护代码前缀规则 | 统一收敛到 `pipeline/mkt.py` |

## 安装

只运行网站不需要安装任何 npm 依赖，也不需要 Node.js。准备 Python 3 即可使用仓库自带静态服务器：

```bash
git clone https://github.com/zhangyh066/china-chain.git
cd china-chain

python -m pip install akshare pandas
```

## 快速开始

静态站点需要通过 HTTP 打开，不能直接双击 `index.html` 使用 `file://`，否则 ES Module 会被浏览器 CORS 策略拦截。

**Windows**：双击 `serve.bat`。

**命令行**：

python serve.py 8123

## 数据管线与更新策略

### 一键运行

```bash
# 使用缓存增量更新；已有数据不会因派生规则调整而被迫重爬
python pipeline/run_all.py

# 额外补齐近一年日线，并重建趋势
python pipeline/run_all.py --with-history

# 明确需要刷新行情缓存时才使用
python pipeline/run_all.py --refresh
```

管线按顺序执行：行情财务 → 行业成分 → 概念成分 → 公司筛选 → 基础数据组装 → 推断关系 → 可选历史 → 趋势 → 产业链 → 传导 → 纯度 → 本地披露 → 链内披露 → 健康度 → 静态页预渲染。

### 只重建某个派生层

```bash
python pipeline/build_trends.py             # 已有日线 → 趋势指数
python pipeline/build_chains.py             # 公司档案 → 27 条产业链看板
python pipeline/build_purity.py             # 主营构成 → 概念纯度
python pipeline/build_transmission.py       # 价格与环节指数 → 传导统计
python pipeline/build_chain_disclosure.py   # 披露边 → 链内披露连线
python pipeline/build_health.py             # 各产物日期与覆盖 → 健康度
python pipeline/prerender.py                # 公司/行业静态页与 sitemap
```

### 当前更新策略

- 行情、行业和概念抓取有磁盘缓存；不需要更新的数据不要重爬。
- 日线支持断点续抓、指定公司补抓和分批运行。
- **每日 GitHub Actions 自动抓取已于 2026-10-15 暂停**；需要时手动 dispatch，或本地运行管线。
- 更新只有在 `ci_check.py` 通过后才提交；失败不覆盖线上旧数据。
- 每周一由 Actions 生成一次周报 Issue，内容只读仓库已有数据、不联网；数据滞后时标题仍使用真实数据区间，不伪装成最新一周。

单独生成周报：

```bash
python pipeline/weekly_report.py
```

## 已知限制与 Roadmap

### 已知限制

- 公司池为筛选结果，不是全 A 股；当前行业池不含交通运输、商贸零售，因此物流等链条无法可靠补全。
- 披露关系只覆盖公开前五大客户/供应商的一部分；匿名披露普遍，不能据此计算完整供应网络。
- 推断边只用于结构示意，不能作为“谁给谁供货”的事实引用。
- 行情与趋势目前存在滞后；每日自动抓取暂停，使用时先看数据健康度。
- 等权趋势会受成分股上市、退市与环节归属变化影响，不构成严格可投资回测指数。
- 传导视图展示统计共动，不等于因果证明，更不输出买卖信号。
- 前端为单文件主应用，没有路由级代码分割；测试以端到端为主，没有完整单元测试体系。

### Roadmap

- [x] 公司、行业、环节三级趋势与公司双基准对照
- [x] 27 条产业链上中下游分层与品类链区分
- [x] 真实客户/供应商披露、反向索引与地图叠层
- [x] 数据健康度与离线每周周报
- [x] 检验并停止不具备证据支持的收益预测方向
- [ ] 在不重复爬取的前提下恢复可控的数据更新节奏
- [ ] 扩充披露年份与公司覆盖，改善匿名关系造成的缺口
- [ ] 为链条配置补充更多可核验的产品价格与公开来源
- [ ] 将更多人工环节归类与披露证据做成可审计记录
